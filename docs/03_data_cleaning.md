# 数据清洗方案（ODS → DWD）

> 原则先行：**ODS 层忠实保存，DWD 层才做清洗。**>   
> 清洗不等于删除。本方案对绝大多数异常采用**打标（flag）而非删除**，>   
> 只有"确定无法使用"的数据才排除。理由见第三节。

### 关于「166 条发货早于下单」的深入结论

不是时区问题。时间差分布：

| 提前小时数           | 条数  |
| --------------- | --- |
| 0 小时（同小时内分钟颠倒）  | 121 |
| 1 小时            | 39  |
| 2 小时            | 4   |
| 101 小时          | 1   |
| 4,109 小时（171 天） | 1   |

**160 条属于「同一小时内的顺序误差」**（采集精度问题，业务影响可忽略），  
真正需要关注的是 2 条超过 24 小时的异常。

→ 因此清洗策略：**标记 `is_time_anomaly`（阈值 24 小时），不删除**。

## 二、八个清洗任务（按执行顺序）

### 任务 1：geolocation 邮编去重 → `dim_geolocation`

**问题**：100 万行，19,015 个邮编，平均每个邮编 52.6 行，最多 1,146 行。  
直接 JOIN 会导致**事实表行数膨胀 52 倍**——这是最典型的「未去重维度表导致指标翻倍」事故。

**聚合规则**：

| 字段  | 规则                                                 | 理由                             |
| --- | -------------------------------------------------- | ------------------------------ |
| 经纬度 | `AVG()`，**先排除越界坐标**（lat 不在 -34~~5、lng 不在 -74~~-34） | 42 条越界坐标会把均值拉飞；去掉后取平均代表邮编中心    |
| 城市  | **众数**（出现次数最多的），用 `ROW_NUMBER()` 取第 1              | 同一邮编有 551 个对应多城市名（拼写不一致），取众数最稳 |
| 州   | 众数                                                 | 同上                             |
| 源行数 | `COUNT(*)`                                         | 保留聚合痕迹，便于回溯                    |

**为什么不用 `MIN/MAX` 或任取一条？**  
任取一条 = 随机性，同一份数据重跑结果可能不同（不可复现）；  
`MIN/MAX` = 取边界值，可能取到离群点；  
`AVG` + 排异常 = 稳定、可复现、可解释。

**为什么城市用众数而不是 `MIN`？**  
`MIN` 是字典序最小，会取到拼写怪异的那一条。众数代表"大多数记录这么写"。

---

### 任务 2：客户身份标准化 → `dim_customer`

**这是本项目最重要的业务理解点。**

| 字段                   | 含义                                                   |
| -------------------- | ---------------------------------------------------- |
| `customer_id`        | **每下一个订单就生成一个新值**（99,441 个订单 → 99,441 个 customer_id） |
| `customer_unique_id` | **同一个人的真实身份，跨订单不变**（只有 96,096 个）                     |

**如果算复购率用 `customer_id`，结果永远是 0%**——因为每个 customer_id 只出现一次。  
用 `customer_unique_id` 算出真实复购：

- 下过 1 单：93,099 人
- 下过 2 单：2,745 人
- 下过 3 单：203 人
- 4 单及以上：48 人
- **复购率 = (96,096 − 93,099) / 96,096 ≈ 3.12%**

**设计**：以 `customer_unique_id` 为主键建真实客户维度，冗余首单信息、  
订单数、首末单时间。

### 任务 5：订单事实 → `dwd_orders`

**派生指标**（这是可直接引用的指标）：

| 派生字段              | 计算方式                            | 业务含义                                          |
| ----------------- | ------------------------------- | --------------------------------------------- |
| `delivery_days`   | `DATEDIFF(签收时间, 下单时间)`          | 实际配送时长                                        |
| `estimated_days`  | `DATEDIFF(预计送达, 下单时间)`          | 承诺时长                                          |
| `is_late`         | 按天判断：`DATEDIFF(实际签收, 预计送达) > 0` | 是否延迟（1/0）<br />⚠️第 5 步修正：原按时间戳比较会把"当天送达"误判为延迟 |
| `late_days`       | `DATEDIFF(实际, 预计)`，提前为负         | 延迟天数                                          |
| `is_time_anomaly` | 发货比下单早 **超过 24 小时**             | 标记严重时间异常                                      |
| `is_delivered`    | `order_status = 'delivered'`    | 是否成交                                          |

**关键决策：不过滤非 delivered 订单。**  
理由：`canceled` / `unavailable` 本身就是业务分析对象（取消率、缺货率）。  
过滤动作放在**查询时**（`WHERE is_delivered = 1`），而不是建表时删掉。

- 关联 `dim_customer` 拿 `customer_unique_id`（避免每次都多一次 JOIN）
- 派生 `item_total = price + freight_value`

### 任务 7：支付聚合 → `dwd_payments`

**问题**：原表 103,886 行 > 99,441 个订单 → 一单可能多笔支付（组合支付）。

**聚合规则**：

- `payment_total` = `SUM(payment_value)`
- `payment_count` = `COUNT(*)`
- `max_installments` = `MAX(payment_installments)`
- `main_payment_type` = 金额最大的那种支付方式（众数会失真，按金额取更合理）

**为什么不能直接 JOIN 原表？**  
一单多支付时，JOIN 会让订单金额重复计算 → GMV 虚高。必须先聚合到订单粒度。

**9 条支付金额为 0**：保留并标记，属于业务异常但不应删除。

---

### 任务 8：评价去重 → `dwd_reviews`

**问题**：555 个订单有多条评价（100,000 条评价 → 99,441 个订单）。

**去重规则：每个订单取 `review_creation_date` 最新的一条。**

**为什么取最新而不是平均分/第一条？**

| 方案        | 问题                           |
| --------- | ---------------------------- |
| 取平均分      | 评分变成 4.5 这种小数，破坏"1-5 星整数"的语义 |
| 取第一条      | 可能是用户误点后重评，第一条不代表最终态度        |
| **取最新** ✅ | 评价代表"最终态度"，用户重评通常是修正之前的评价    |

**同时保留 `review_count`**，让下游知道这个订单被评过几次（评价反复修改的订单可能本身有问题）。

## 三、清洗原则：为什么"打标"优于"删除"

| 做法               | 后果                             |
| ---------------- | ------------------------------ |
| 直接删掉 166 条时间异常   | 丢失 166 条真实订单，GMV 被低估，且**无法回溯** |
| 直接删掉 610 条品类缺失商品 | 丢失有成交的商品，品类分析出现盲区              |
| 直接删掉 9 条零支付订单    | 免费赠品/全额优惠订单被误判为脏数据             |
| **打标，查询时按需过滤** ✅ | 数据完整，分析可复现，随时能回答"这些异常到底有多少"    |

**核心逻辑**：清洗层不是"把数据变干净"，而是"把数据的质量状况**显式记录下来**"。  
删掉脏数据 = 假装问题不存在；打标 = 承认问题并交给业务方决策。

| dim_customer    | 96,096     | ✅                |
| dim_product     | 32,951     | ✅                |

| dwd_orders      | 99,441     | ✅                |
| dwd_order_items | 112,650    | ✅                |
| dwd_payments    | **99,440** | ⚠️ 比订单少 1（见 6.4） |
| dwd_reviews     | 99,441     | ✅                |

执行耗时 22 秒（geolocation 百万行聚合占大部分）。

### 6.2 ★ 维度去重验证（最关键）

| 场景                                                  | 行数         |
| --------------------------------------------------- | ---------- |
| `SELECT COUNT(*) FROM dwd_orders`                   | 99,441     |
| `dwd_orders JOIN dim_customer JOIN dim_geolocation` | **99,441** |

**结论：JOIN 维度表后行数不变，没有膨胀。**  
这是检验维度表去重是否成功的唯一硬标准——如果变成 500 万行，就说明某个维度没去重。

### 6.3 ★ 复购率两种口径对比（核心业务陷阱）

| 口径                           | 客户数    | 复购人数  | 复购率       |
| ---------------------------- | ------ | ----- | --------- |
| `customer_id`（**错误**）        | 99,441 | 0     | **0.00%** |
| `customer_unique_id`（**正确**） | 96,096 | 2,997 | **3.12%** |

用错字段会得到 0%，而且不报错。这个对比建议直接记住，写进总结很有说服力。

### 6.4 数据缺陷：1 个订单无支付记录

订单 `bfbd0f9bdef84302105ad712db648a6c`：

- 状态 `delivered`（已签收）
- 有 3 个商品行，金额 143.46
- **源数据里完全没有支付记录**

**处理方式：保留现状，不补造数据。**  
查询支付相关指标时必须用 `LEFT JOIN dwd_payments`，否则这个订单会消失。

### 6.5 GMV 三种口径（对账差异）

| 口径                      | 金额（元）         | 说明                      |
| ----------------------- | ------------- | ----------------------- |
| 商品金额（仅 `price`）         | 13,591,643.70 | 不含运费                    |
| 明细金额（`price + freight`） | 15,843,553.24 | 常用 GMV 口径               |
| 支付金额（`payment_total`）   | 16,008,872.12 | 比明细多 165,318.88（+1.04%） |

**支付口径 > 明细口径 1.04%**，可能来自分期手续费或源系统记账差异。  
**小结**：报 GMV 时必须说明口径，不同口径差 1% 在业务上就是百万级差异。

### 6.7 ★★ 数据边界：做时间趋势分析前必须知道

| 时间                | 订单数         | 说明           |
| ----------------- | ----------- | ------------ |
| 2016-09           | 4           | 起步期，无参考价值    |
| 2016-10           | 324         | 起步期          |
| **2016-11**       | **0**       | **整月缺失**     |
| 2016-12           | 1           | 仅 1 单        |
| 2017-01 ~ 2018-08 | 800 ~ 7,544 | ✅ **正常分析窗口** |
| 2018-09           | 16          | 数据截断         |
| 2018-10           | 4           | 数据截断         |

**这是最容易出错、也最容易被评审抓住的点。**

如果直接画月度趋势图，会看到 2016 年几乎为零、2018 年 9 月断崖下跌——  
但这是**数据截断**，不是业务下滑。

**正确做法**：所有时间趋势分析必须限定

```sql
WHERE purchase_ts >= '2017-01-01' AND purchase_ts < '2018-09-01'
```

**实现说明**：

> 做月度趋势前我先看了各月订单量，发现 2016-09~~12 和 2018-09~~10 订单量极低，中间还缺 2016-11 整月。这不是业务波动，是数据采集窗口的边界。所以我把分析窗口收敛到 2017-01 到 2018-08，避免把数据截断误读成业务下滑。
