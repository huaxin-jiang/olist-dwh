# 性能优化报告

> 数据库：MySQL 8.0.43>   
> 数据量：dwd_orders 99,441｜dwd_order_items 112,650｜dwd_reviews 100,000>   
> 测量方式：`SET profiling=1` + `SHOW PROFILES`，交替执行 3 轮取中位数>   
> 判定依据：`EXPLAIN` 的 `type`、`rows`（确定性输出，不受缓存影响）

---

## 零、方法论：为什么不能只看耗时

这一节先讲清楚，因为它决定后面所有结论可信不可信。

**毫秒级耗时会骗人。** 同一个查询在冷缓存和热缓存下，实测能差 3 倍以上：

| 查询               | 首次执行（冷） | 稳定执行（热） |
| ---------------- | ------- | ------- |
| `DATE_FORMAT` 过滤 | 0.104s  | 0.031s  |
| `COUNT(*)` 全表    | 0.121s  | 0.033s  |

如果把冷启动的 0.104s 和热态的 0.0025s 对比，会得出"快 42 倍"——**这是假的**，差异主要来自磁盘 IO 而非 SQL 本身。

所以本报告采用两条纪律：

1. **交替执行 3 轮取中位数**，消除缓存漂移（A/B/A/B/A/B，不是 AAA 然后 BBB）
2. **用 `EXPLAIN` 的 `type` 和 `rows` 作为主要证据**，耗时作为辅助

`rows` 是优化器的确定性估计，换台机器结论也一样。汇报时说"扫描行数从 98,267 降到 14,030"，比说"快了 13 倍"更经得起追问。

## 一、慢查询清单（实测）

先测 11 个业务查询，找出真正慢的：

| 查询                      | 耗时         | 是否是问题               |
| ----------------------- | ---------- | ------------------- |
| 相关子查询求订单汇总              | **0.90s**  | ❌ 慢，N+1             |
| 多表连接 + 品类分组             | 0.65-0.88s | ⚠️ 慢，但主要是数据量使然      |
| `LIKE '%produto%'` 全文搜索 | 0.15s      | ⚠️ 必然全扫，可用全文索引解决    |
| `DATE_FORMAT` 按月份筛选     | 0.031s     | ❌ 看着不慢，但比正确写法慢 13 倍 |
| 正常范围查询（对照）              | 0.0025s    | ✅ 基准                |
| 隐式类型转换查询                | 0.084s     | ❌ 全表扫描              |

注意第三行和第四行：**`DATE_FORMAT` 那个只用了 31 毫秒，从"慢查询"标准（>1s）看完全正常，但它其实是全表扫描。** 数据量涨 100 倍后它就是 3 秒。这就是为什么必须看 `EXPLAIN`，不能只看耗时。

## 二、优化 1：消除 N+1 相关子查询（0.903s → 0.287s）

### 问题查询

业务需求：查每个订单的商品数和总金额。

```sql
SELECT o.order_id,
       (SELECT COUNT(*) FROM dwd_order_items i WHERE i.order_id = o.order_id) AS cnt,
       (SELECT SUM(i.item_total) FROM dwd_order_items i WHERE i.order_id = o.order_id) AS amt
FROM dwd_orders o;
```

### 诊断

```sql
EXPLAIN ...
```

| id | select_type            | table | type  | key           | rows   | Extra       |
| -- | ---------------------- | ----- | ----- | ------------- | ------ | ----------- |
| 1  | PRIMARY                | o     | index | idx_delivered | 98,267 | Using index |
| 3  | **DEPENDENT SUBQUERY** | i     | ref   | PRIMARY       | 1      | NULL        |
| 2  | **DEPENDENT SUBQUERY** | i     | ref   | PRIMARY       | 1      | Using index |

**关键不是 `type`，是 `select_type = DEPENDENT SUBQUERY`。**

单次子查询只查 1 行（`rows=1`，走了主键），效率很高。但 `DEPENDENT` 意味着它**依赖外层每一行**：

> 98,267 个订单 × 2 个子查询 = **196,534 次独立查询**

每次查询有固定的解析、优化、B+ 树下降开销（约 4-5 微秒）。196,534 × 4.5μs ≈ 0.88s——**耗时几乎全部来自调用次数，而不是数据量**。

这就是数据库里最经典的 **N+1 查询问题**：单次都快，加起来就慢。

### 优化

把"逐行查询"改成"一次聚合 + 一次连接"：

```sql
SELECT o.order_id, i.cnt, i.amt
FROM dwd_orders o
LEFT JOIN (
    SELECT order_id, COUNT(*) AS cnt, SUM(item_total) AS amt
    FROM dwd_order_items
    GROUP BY order_id
) i ON o.order_id = i.order_id;
```

### 结果

| 指标         | 优化前                    | 优化后                      |
| ---------- | ---------------------- | ------------------------ |
| 耗时（3 轮中位数） | 0.903s                 | **0.287s**               |
| 提速         | —                      | **3.1 倍**                |
| 子查询/扫描次数   | 196,534 次索引查找          | 2 次表扫描                   |
| 执行计划       | DEPENDENT SUBQUERY × 2 | DERIVED（覆盖索引扫描）+ 一次 JOIN |

优化后的执行计划里，派生表用上了 `idx_item_order_amount(order_id, item_total)`，`Extra: Using index`——**全程不碰数据页，只读索引**。

### 一个失败的尝试（也值得写）

我先试了"直接 JOIN + GROUP BY"，不建派生表：

```sql
SELECT o.order_id, COUNT(i.order_id), SUM(i.item_total)
FROM dwd_orders o LEFT JOIN dwd_order_items i ON o.order_id = i.order_id
GROUP BY o.order_id;
```

结果 **0.33s**，比派生表写法（0.29s）还慢一点。原因是 99,441 个分组要建临时表，两种写法代价相当。

**教训**：不是所有"看起来更简洁"的改写都更快。改完必须测。

## 三、优化 2：消除索引失效（0.031s → 0.0025s，扫描行数降 86%）

### 问题

按月份筛选订单，业务上很自然会写成：

```sql
WHERE DATE_FORMAT(purchase_ts, '%Y-%m') = '2017-11'
```

### 诊断

| 写法                                               | type      | key             | rows       |
| ------------------------------------------------ | --------- | --------------- | ---------- |
| `DATE_FORMAT(purchase_ts,'%Y-%m')='2017-11'`     | **ALL**   | NULL            | **98,267** |
| `purchase_ts >= '2017-11-01' AND < '2017-12-01'` | **range** | idx_purchase_ts | **14,030** |

`idx_purchase_ts` 索引明明存在，但完全用不上——因为 B+ 树里存的是 `purchase_ts` 的原始值，不是 `DATE_FORMAT` 后的字符串。优化器只能逐行计算函数再比较。

### 结果

| 指标     | 优化前       | 优化后                 |
| ------ | --------- | ------------------- |
| 扫描行数   | 98,267    | **14,030**（降 85.7%） |
| type   | ALL（全表扫描） | range（索引范围扫描）       |
| 耗时（热态） | 0.031s    | **0.0025s**（12.4 倍） |

**改写原则：把函数从列上挪到常量上。** 任何 `WHERE f(col) = 常量` 都可以想办法改写成 `WHERE col BETWEEN a AND b`。

## 四、索引失效 8 场景实测（含 2 条辟谣）

完整脚本见 `sql/07_index_invalidation.sql`。下表是实测结果：

| # | 场景              | 失效写法                                | type / rows       | 正确写法              | type / rows    | 结论                      |
| - | --------------- | ----------------------------------- | ----------------- | ----------------- | -------------- | ----------------------- |
| 1 | 函数包裹列           | `DATE_FORMAT(ts,'%Y-%m')='2017-11'` | **ALL / 98,267**  | `ts BETWEEN ...`  | range / 14,030 | ✅ 确实失效                  |
| 2 | 隐式类型转换          | `varchar_col = 1037`                | **ALL / 19,288**  | `= '01037'`       | const / 1      | ✅ 确实失效                  |
| 3 | 前导模糊            | `LIKE '%table%'`                    | index / 32,915    | `LIKE 'bed%'`     | range / 4,784  | ✅ 确实失效                  |
| 4 | OR 跨未索引列        | `state='SP' OR city='x'`            | **ALL / 95,532**  | 单列条件              | ref / 47,766   | ✅ 确实失效                  |
| 5 | `!=` / `NOT IN` | `status <> 'delivered'`             | **range / 2,963** | —                 | —              | ❌ **辟谣，没失效**            |
| 6 | 跳过最左前缀          | `month = 11`                        | **range / 9,826** | 带前导列              | ref / 13,408   | ⚠️ **部分失效，有 skip scan** |
| 7 | 列参与运算           | `order_count + 1 > 2`               | index / 95,532    | `order_count > 1` | range / 2,997  | ✅ 确实失效                  |
| 8 | 选择性过低           | `is_delivered = 1`                  | ref / **49,133**  | —                 | —              | ⚠️ 用了索引等于没用             |

> 注：场景 1、3、7 的 `type=index` 表示"全索引扫描"，扫的仍是全部行，等价于全表扫描，只是扫索引页而不是数据页。

### 辟谣 1：`!=` 和 `NOT IN` 在 MySQL 8 上不失效

网上到处说"不等于会导致索引失效"。实测：

```
WHERE order_status <> 'delivered'          → type=range, rows=2,963
WHERE order_status NOT IN ('delivered','shipped') → type=range, rows=1,856
```

MySQL 8 会把 `<> x` 等价改写成 `< x OR > x` 两个区间，索引照用，**而且比等值查询还快**（等值 `= 'delivered'` 要扫 49,133 行）。

真正的规律是**代价驱动**：如果被排除的值极少，剩下 99.4% 都要返回，优化器才会放弃索引：

```
WHERE order_status != 'canceled'   → type=range, rows=49,135   ← 扫半张表，索引形同虚设
```

所以正确的说法是：**`!=` 不必然失效，取决于剩余数据量占比。** 能说出这句话，比背"不等于会失效"高一个层次。

### 辟谣 2：跳过最左前缀，MySQL 8 有 Skip Scan 兜底

索引是 `idx_year_month(purchase_year, purchase_month)`，只查 `purchase_month = 11`：

```
type=range, key=idx_year_month, rows=9,826, Extra: Using index for skip scan
```

**`Using index for skip scan`** —— MySQL 8.0.13 引入的优化：当前导列基数很小（本例 `purchase_year` 只有 3 个不同值）时，优化器会枚举前导列的每个值，逐个跳查，相当于把单列查询拆成"3 次带前导列的查询"。

**但它不是万能的。** 换个高基数前导列立刻失效：

```sql
-- PRIMARY(order_id, order_item_id)，order_id 基数 98,666
WHERE order_item_id = 1
→ type=index, rows=111,435, key=idx_product   ← 退化为全索引扫描
```

**结论：最左前缀原则依然成立，只是 MySQL 8 在"前导列基数极低"时提供了兜底。** 设计复合索引时仍然要把最常用的过滤列放在最左边。

## 五、反例：加了一个"看起来合理"的索引，结果变慢了

这是本文最有价值的一节。

### 做了什么

多表查询里有个条件 `is_delivered = 1 AND purchase_date BETWEEN ...`。直觉上应该建复合索引：

```sql
ALTER TABLE dwd_orders ADD INDEX idx_deliv_date (is_delivered, purchase_date);
```

### 结果：变慢了

| 状态   | 3 轮耗时                            | 中位数       |
| ---- | -------------------------------- | --------- |
| 加索引前 | 0.65 / 0.70 / 0.65               | **0.68s** |
| 加索引后 | 0.71 / 0.76 / 0.78 / 0.84 / 0.79 | **0.78s** |

**慢了 15%。**

### 原因

查一下过滤条件到底能筛掉多少数据：

```sql
SELECT COUNT(*) FROM dwd_orders WHERE purchase_date BETWEEN '2017-01-01' AND '2018-08-31';
-- 99,092
```

**99,092 / 99,441 = 99.65%。**

日期窗口筛掉了 0.35% 的数据。这个复合索引的第二列（purchase_date）**没有任何过滤能力**，索引退化成"只有 is_delivered 一列有用"，而 `is_delivered` 选择性只有 0.002%（2 个值 / 99,441 行）。

同时优化器并没有选这个新索引（`EXPLAIN` 显示仍走 `idx_delivered`），但表上多了一个索引意味着：

- 索引页占用了 buffer pool 空间，挤掉了真正有用的数据页
- 统计信息变化影响了优化器估算

已经 `DROP INDEX` 删除。

### 教训

**"这个列在 WHERE 里" ≠ "这个列该建索引"。** 判断标准是**选择性**：

$\text{选择性} = \frac{\text{不同值个数}}{\text{总行数}}$

实测本库各列：

| 列                  | 不同值    | 总行数    | 选择性    | 适合建索引      |
| ------------------ | ------ | ------ | ------ | ---------- |
| order_id           | 99,441 | 99,441 | 100%   | ✅ 主键       |
| customer_unique_id | 96,096 | 99,441 | 96.6%  | ✅ 适合       |
| order_status       | 8      | 99,441 | 0.008% | ⚠️ 单独建意义不大 |
| is_delivered       | 2      | 99,441 | 0.002% | ❌ 不该建      |

**选择性低于 10% 的列，单独建索引基本没有优化价值。**

## 六、那 Q1 为什么一直在全表扫描？

顺便发现的一个设计问题：Q1（月度 GMV）用 `purchase_date` 过滤，但索引建在 `purchase_ts` 上：

```sql
EXPLAIN SELECT ... WHERE purchase_date BETWEEN '2017-01-01' AND '2018-08-31';
-- type=ALL, rows=98,267, key=NULL
```

`purchase_date` 是从 `purchase_ts` 派生的日期列，DWD 层加了这个字段但没建索引。

**要不要补一个？答案是不要**——原因同上：这个范围覆盖 99.65% 的数据，加了也是白加。

**正确的做法是把过滤条件改成走已有索引的列**，或者干脆接受全表扫描（当查询本来就要读大部分数据时，顺序全表扫描比"索引 + 大量回表"更快，这是优化器的正确判断）。

> 这一条能讲清楚，说明你理解了"索引不是越多越好"，而不是背"WHERE 列都要建索引"。

## 七、最终的索引决策

| 索引                                             | 动作         | 理由                                    |
| ---------------------------------------------- | ---------- | ------------------------------------- |
| `idx_item_order_amount (order_id, item_total)` | **新增**     | 让订单汇总的派生表实现覆盖索引扫描（`Using index`），避免回表 |
| `idx_deliv_date (is_delivered, purchase_date)` | **新增后又删除** | 第二列无过滤能力（覆盖 99.65%），实测慢 15%           |
| `idx_delivered (is_delivered)`                 | 保留         | 选择性极低，但已有查询在用；生产中可考虑删除                |
| 其余已有索引                                         | 保留         | 均服务于主键/外键连接或高频过滤                      |

**只加了一个索引。** 这不是保守，是实测结论——在这个数据量和查询模式下，真正的瓶颈是查询写法，不是索引缺失。

## 九、结论表述（可直接用）

> 针对订单汇总查询的 N+1 问题，通过 `EXPLAIN` 定位到 98,267 次 `DEPENDENT SUBQUERY` 执行，改写为派生表聚合 + LEFT JOIN，查询耗时从 0.90s 降至 0.29s（提升约 3 倍），子查询执行次数从 196,534 次降至 2 次表扫描。
>
> 系统验证 8 类索引失效场景（函数包裹、隐式类型转换、前导模糊、OR 跨列、列运算、最左前缀、低选择性），将月份筛选查询的扫描行数从 98,267 降至 14,030（降 85.7%）；并通过实测发现 `!=` 与 `NOT IN` 在 MySQL 8 中会改写为 range 扫描，纠正了对索引失效规则的教条理解。

**为什么这两句经得起追问：**

- 有具体数字，且数字来源可复现（脚本在仓库里）
- 说了"3.1 倍"而不是"100 倍"——**夸张的数字反而会被评审怀疑**
- 第二句体现了"不迷信网上的规则，自己验证"——这是工程判断力

## 十、设计问答

**Q：怎么定位慢查询？**

> 三层。第一层，开 `slow_query_log` + 设 `long_query_time`，让超时 SQL 自动落盘，这是发现问题的入口。第二层，对可疑 SQL 跑 `EXPLAIN`，看 `type`（是否 ALL）、`rows`（扫描行数）、`Extra`（是否 Using filesort / Using temporary）。第三层，`EXPLAIN ANALYZE` 看实际执行时间和实际行数，验证优化器估算准不准。我这个项目里把 `long_query_time` 从默认 10 秒改成了 1 秒，因为大部分查询优化后都在毫秒级，10 秒根本抓不到。

**Q：`EXPLAIN` 里你最关注哪几列？**

> `type`、`rows`、`Extra`。`type` 看访问方式，ALL 是全表扫描，index 是全索引扫描（也等于全扫），range/ref/const 才是真正定位。`rows` 看扫描量，比耗时稳定。`Extra` 看有没有 `Using filesort`（排序没走索引）、`Using temporary`（分组用了临时表）、`Using index`（覆盖索引，最好）。我一般先用 rows 判断有没有优化空间，再看 Extra 判断瓶颈在哪。

**Q：索引失效有哪些情况？**

> 常见的有：列被函数包裹、隐式类型转换、前导模糊 LIKE、OR 连接了没索引的列、列参与运算、跳过复合索引最左列、选择性太低。但要补充一点——`!=` 和 `NOT IN` 在 MySQL 8 上**不会**失效，优化器会改写成 range 扫描。这个我用真实数据验证过。

**Q：为什么加了索引反而变慢？**

> 我踩过。给 `(is_delivered, purchase_date)` 建了复合索引，结果慢 15%。原因是查询的日期窗口覆盖了 99.65% 的数据，第二列完全没有过滤能力，索引退化成只有第一列有用；而 `is_delivered` 只有 2 个值，选择性 0.002%。多出来的索引页还挤占了 buffer pool。我查了数据分布后把它删了。**索引的价值取决于选择性，不是"有没有出现在 WHERE 里"。**

**Q：N+1 问题是什么？怎么发现？**


> 就是外层每行都触发一次子查询。`EXPLAIN` 里看 `select_type = DEPENDENT SUBQUERY` 就是它。单次子查询 `rows=1` 很快，但 98,267 行就是 196,534 次调用，每次固定开销 4-5 微秒，加起来 0.9 秒。改法是把逐行查询变成一次聚合 + 连接，执行次数从 196,534 降到 2。

**Q：为什么不直接把所有 WHERE 列都建上索引？**

> 三个代价：一是写放大，每次 INSERT/UPDATE 都要维护所有索引；二是占空间和 buffer pool，挤掉真正有用的数据页；三是误导优化器。我这个库 `is_delivered` 只有 2 个值，选择性 0.002%，建了索引也是扫半张表。**建索引前先算选择性和数据分布，不要凭直觉。**
