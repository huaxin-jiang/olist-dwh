# 业务分析报告

> 数据窗口：2017-01-01 ~ 2018-08-31>   
> 数据源：Olist 巴西电商公开数据集（真实脱敏数据）>   
> 分析层：DWD / DIM

---

## 一、口径定义（先定口径，再看数字）

任何一份数据报告，最有价值的不是数字，而是**口径**。同一份数据换个口径，结论可能完全相反。

| 指标   | 本报告口径                                            | 为什么这么定                            |
| ---- | ------------------------------------------------ | --------------------------------- |
| 订单数  | `COUNT(DISTINCT order_id)`                       | `COUNT(*)` 会按明细行计数，一单多商品会被重复计算    |
| GMV  | `SUM(item_total)` = 商品价 + 运费                     | 只看 `price` 会漏掉 16.5% 的运费收入        |
| 有效订单 | `order_status NOT IN ('canceled','unavailable')` | 未成交订单计入会虚增 GMV                    |
| 客单价  | `GMV / 订单数`                                      | 不是 `AVG(明细价格)`——那算的是商品均价          |
| 复购   | 按 `customer_unique_id` 跨日下单                      | 按 `customer_id` 会得到 0%；同日多单是拆单    |
| 延迟   | `DATEDIFF(送达日, 承诺日) > 0`                         | 按天判断，当日达成本就算准时                    |
| 留存   | 分母是该月新增客户数                                       | 不是该月订单数                           |
| 时间窗口 | 2017-01 ~ 2018-08                                | 2016 年数据刚起步，2018-09 后被截断，纳入会造成假下跌 |

## 三、十一个查询的业务结论

### Q1 月度 GMV 趋势：一年半增长 7 倍，但已进入平台期

| 时间      | GMV           | 环比          |
| ------- | ------------- | ----------- |
| 2017-01 | 136,943       | —           |
| 2017-11 | **1,172,192** | **+53.28%** |
| 2017-12 | 861,527       | −26.50%     |
| 2018-03 | 1,152,657     | +17.68%     |
| 2018-08 | 996,974       | −4.12%      |

**三个结论：**

1. **2017-11 是明确峰值**（+53.28%），对应巴西黑色星期五大促；12 月回落 26.5% 是典型的大促透支效应，不是业务恶化。
2. **2018 年起进入平台期**：2-8 月 GMV 稳定在 100-116 万之间，环比在 ±11% 内波动，没有明显增长趋势。
3. **增长主要来自订单量而非客单价**：2017-01 的 787 单到 2018-08 的 6,421 单，增长 8.2 倍；客单价基本持平。

> **技术点**：用 `LAG()` 算环比，一次排序扫描完成。用自连接（self-join）需要两次全表扫描 + 连接，数据量大时差距是数量级的。
>
> **对外汇报时**：不要只念数字，要说"11 月峰值来自大促、12 月回落是大促透支、2018 年进入平台期需要新的增长点"——这是业务判断，不是 SQL 演示。

### Q2 客单价：均值比中位数高 52%，报均值会误导决策

| 指标      | 金额         |
| ------- | ---------- |
| 均值      | 160.19     |
| 中位数 P50 | **105.28** |
| P90     | 306.97     |
| P99     | 1,055.92   |
| 最大值     | 13,664.08  |

**结论**：金额分布严重右偏——少数大额订单把均值拉高了 52%。**运营决策要用中位数 105 元，不是均值 160 元。**

如果按均值 160 元设计"满 160 减 20"的活动，实际上会覆盖不到一半的订单（因为一半订单低于 105 元），活动效果会远低于预期。

> **技术点**：`ROW_NUMBER()` + `CEIL(total * 0.5)` 取分位数。MySQL 8 没有 `PERCENTILE_CONT`，只能用窗口函数模拟。
>
> **要点**：为什么电商必报中位数？——右偏分布下均值不具代表性，这是统计学常识，但很多候选人只会写 `AVG()`。

### Q3 品类结构：TOP10 贡献 62%，集中度中等

| 排名 | 品类                    | GMV       | 占比    | 累计         |
| -- | --------------------- | --------- | ----- | ---------- |
| 1  | health_beauty         | 1,432,213 | 9.13% | 9.13%      |
| 2  | watches_gifts         | 1,294,824 | 8.26% | 17.39%     |
| 3  | bed_bath_table        | 1,239,780 | 7.90% | 25.29%     |
| 4  | sports_leisure        | 1,144,754 | 7.30% | 32.59%     |
| 5  | computers_accessories | 1,049,201 | 6.69% | 39.28%     |
| 10 | garden_tools          | 578,060   | 3.69% | **62.37%** |

**结论**：

1. **TOP10 占 62.37%**，不符合典型二八法则（TOP20% 贡献 80%）。71 个品类里，长尾部分仍然贡献 37.6% 的 GMV，说明平台是"多品类均衡"结构，不是靠单品类支撑。
2. **health_beauty（美妆个护）是第一大类**，占比 9.13%，且客单价不高但订单量大（8,757 单）——典型的高频品类，适合做复购运营。
3. **bed_bath_table 订单数最多（9,394 单）但 GMV 只排第 3**——客单价低，走量型品类。

> **技术点**：`SUM(gmv) OVER (ORDER BY gmv DESC)` 累计求和，一行 SQL 出帕累托曲线，不用写循环、不用导到 Excel。

### Q4 地域：SP 一州占 37%，物流质量南北差距 4 倍

| 州  | 订单数    | GMV       | GMV占比      | 平均配送天数 | 延迟率        |
| -- | ------ | --------- | ---------- | ------ | ---------- |
| SP | 41,005 | 5,861,682 | **37.37%** | 8.7    | **4.50%**  |
| RJ | 12,653 | 2,105,165 | 13.42%     | 15.2   | **12.15%** |
| MG | 11,463 | 1,838,341 | 11.72%     | 11.9   | 4.59%      |
| RS | 5,395  | 873,656   | 5.57%      | 15.2   | 6.10%      |
| BA | 3,342  | 606,223   | 3.87%      | 19.3   | 12.17%     |
| PR | 4,966  | 792,223   | 5.05%      | 11.9   | 4.06%      |

**结论**：

1. **TOP3 州（SP/RJ/MG）占 62.5%**，其中圣保罗州（SP）单州占 37.37%——这是巴西经济地理的典型特征，不是数据问题。
2. **SP 的物流效率是全国的标杆**：8.7 天送达、4.50% 延迟率。而东北部的 AL 要 24.4 天、21.41% 延迟率——**配送时长差 2.8 倍，延迟率差 4.8 倍**。
3. **RJ（里约）是明确的异常点**：GMV 排第 2（13.42%），配送 15.2 天、延迟率 12.15%，而体量相近的 MG 只有 11.9 天、4.59%。**RJ 的延迟率是 MG 的 2.6 倍**，同为东南部却差这么多，不是地理位置能解释的，值得单独排查分拣中心或承运商。

> **技术点**：先把明细聚合到订单粒度，再 JOIN 维度表。顺序反了会让 112,650 条明细去乘维度行数，GMV 直接翻倍。
>
> **要点**：一个客户属于哪个州？——取首单地址。同一个 `customer_unique_id` 的州字段在源数据里是一致的，可以直接 GROUP BY。

### Q5 复购：3.04% 里有 29% 是拆单，真实复购率 2.17%

| 口径               | 复购人数      | 复购率       |
| ---------------- | --------- | --------- |
| 含拆单（同日多单也算）      | 2,875     | 3.04%     |
| **剔除拆单（真实跨日复购）** | **2,054** | **2.17%** |

**复购间隔分布：**

| 间隔      | 次数  | 占比    |
| ------- | --- | ----- |
| 同一天     | 928 | 29.0% |
| 1-3 天   | 129 | 4.0%  |
| 4-30 天  | 564 | 17.6% |
| 31-90 天 | 594 | 18.5% |
| 90 天以上  | 988 | 30.9% |

**结论**：

1. **928 次"复购"发生在同一天**，这不是复购，是**拆单**——同一笔购买因为商品来自不同卖家，被拆成多个订单。按订单数算复购会高估 40%（3.04% vs 2.17%）。
2. **剔除拆单后，真实复购率只有 2.17%**，即 98% 的客户只买一次。这是 Olist 这类平台型电商的典型特征（一次性交易为主）。
3. **复购间隔呈"双峰"**：一个是 4-30 天的短期复购（17.6%），一个是 90 天以上的长期回归（30.9%）。中间 31-90 天是低谷——说明客户要么很快回来，要么很久才回来，中间期几乎没有。

> **这是整个项目里最有价值的一个发现。** 它体现的不是 SQL 能力，而&#x662F;**"拿到一个数先怀疑它"的职业习惯**。3.04% 这个数字本身没有错，但它回答的不是"客户会不会再买"这个问题。

### Q6 留存：M1 留存 0.4-0.7%，留存曲线几乎贴地

| 首购月     | 新增客户  | M1 留存率    | M2    | M3    |
| ------- | ----- | --------- | ----- | ----- |
| 2017-01 | 753   | 0.40%     | 0.27% | 0.13% |
| 2017-08 | 4,130 | **0.68%** | 0.34% | 0.27% |
| 2017-11 | 7,191 | 0.56%     | 0.39% | 0.17% |
| 2018-04 | 6,698 | 0.58%     | 0.31% | 0.24% |

**结论**：

1. **M1 留存率稳定在 0.4-0.7%**，M2 降到 0.2-0.4%，M3 基本归零。这与复购率 2.17% 互相印证——**两个独立口径得出一致结论，说明数据可信**。
2. **留存与获客规模无关**：2017-11 是获客高峰（7,191 人），但 M1 留存（0.56%）并不比 2017-01（0.40%）高多少。大促拉来的客户质量没有明显更差，但也没有更好。
3. **2018-06 之后的 M3 为 0**，是数据窗口截断导致的（窗口到 2018-08），**不是留存归零**——这是 cohort 分析必须注意的"右删失"问题。

> **技术点**：`PERIOD_DIFF` 算月份差、`CASE WHEN month_no = N` 透视成留存表。
>
> **踩过的坑**：`cohort_month` 已经是 `'2017-01'` 字符串，再套 `DATE_FORMAT(..., '%Y%m')` 会返回 NULL，导致 `PERIOD_DIFF` 全是 NULL、**所有留存率算出来都是 0，而且不报错**。正确做法是 `REPLACE(cohort_month, '-', '')`。
>
> **要点**：留存表的最后几行 M2/M3 必然是 0，因为观察期不够。**这不是留存下降，是数据右删失**——能主动指出这一点，说明你真的懂 cohort 分析。

### Q7 配送时效：全国延迟率 6.77%，东北部是重灾区

| 州  | 已签收    | 平均配送天数 | 平均承诺天数 | 延迟率        | 延迟订单平均超时 |
| -- | ------ | ------ | ------ | ---------- | -------- |
| AL | 397    | 24.4   | 33.1   | **21.41%** | 9.5 天    |
| MA | 712    | 21.5   | 30.9   | 17.56%     | 10.5 天   |
| SE | 329    | 21.4   | 31.2   | 15.50%     | 16.2 天   |
| CE | 1,274  | 21.2   | 31.8   | 13.81%     | 15.2 天   |
| RJ | 12,309 | 15.2   | 26.9   | 12.15%     | 13.5 天   |
| SP | 40,390 | 8.7    | 19.7   | **4.50%**  | 8.3 天    |

**结论**：

1. **全国延迟率 6.77%**（6,534 / 96,478）。按修正后的口径，此前算出的 8.11% 是虚高的。
2. **东北部（AL/MA/SE/CE/PI）延迟率 13-21%**，是全国平均的 2-3 倍；东南部（SP/MG）只有 4.5-4.6%。**物流资源严重向东南部倾斜。**
3. **RJ 是"高 GMV + 差物流"的组合**：GMV 第二、延迟率 12.15%，且有 12,309 单的体量。**这是最值得投入改善的市场**——改善 RJ 一州的物流，比改善 AL 能影响 30 倍的订单。

> **业务建议**：物流优化要按"延迟率 × 订单量"排序，不是按延迟率单独排序。AL 延迟率最高但只有 397 单；RJ 延迟率 12% 但有 1.2 万单。**影响面 = 延迟率 × 订单量**，RJ 才是第一优先级。

### Q8 延迟对评分：超过 7 天，差评率从 9.5% 飙到 68%

| 延迟情况      | 订单数    | 平均评分     | 差评率        | 五星率    |
| --------- | ------ | -------- | ---------- | ------ |
| 准时/提前     | 89,672 | 4.28     | 9.52%      | 62.02% |
| 延迟 1-3 天  | 1,869  | 3.28     | 32.42%     | 33.07% |
| 延迟 4-7 天  | 1,802  | **2.09** | **68.04%** | 13.76% |
| 延迟 8-15 天 | 1,637  | 1.67     | 80.21%     | 6.66%  |
| 延迟 15 天以上 | 1,231  | 1.74     | 78.07%     | 7.80%  |

**结论**：

1. **延迟 3 天是临界点**：延迟 1-3 天差评率 32.4%（准时是 9.5%），延迟 4-7 天直接跳到 **68%**。**评分不是线性下降，是断崖式下跌。**
2. **延迟超过 7 天后，差评率见顶**（80% / 78%），说明客户在 7 天后已经"彻底失望"，再多延迟几天也不会更差——**挽回窗口只有 7 天**。
3. **延迟 15 天以上的平均分（1.74）反而略高于 8-15 天（1.67）**，因为这类订单可能伴随退款/取消，客户反而不打分了。

> **业务建议**：物流预警阈值应设在"预计延迟第 3 天"——此时差评率还在 32%，还有挽回空间；到第 4 天就晚了。
>
> **要点（重要）**：这只能证明**相关，不能证明因果**。可能存在混淆变量：偏远地区的订单既慢、商品质量也可能更差。要证明因果需要控制变量（同品类、同价格带内比较），或者做 A/B 测试。**主动说出这一点，比给出结论加分更多。**

### Q9 差评归因：audio 和 office_furniture 的问题不是物流

| 品类               | 订单数   | 差评率        | 平均分  | 该品类延迟率    | 平均客单价  |
| ---------------- | ----- | ---------- | ---- | --------- | ------ |
| audio            | 346   | **22.25%** | 3.82 | 11.85%    | 162.06 |
| office_furniture | 1,248 | **21.88%** | 3.65 | **8.09%** | 267.33 |
| home_confort     | 392   | 18.88%     | 3.88 | 9.44%     | 169.49 |
| unknown          | 1,410 | 18.16%     | 3.98 | 7.23%     | 144.15 |
| bed_bath_table   | 9,267 | 16.56%     | 3.98 | 7.43%     | 132.15 |

**结论**：

1. **office_furniture 是典型的"非物流问题"**：差评率 21.88%（全站 15.03%），延迟率 8.09% 只略高于全站 6.77%，**远不足以解释 1.46 倍的差评率差距**。问题大概率在商品本身——组装复杂、实物与描述不符、或运输中损坏。
2. **audio 的延迟率 11.85% 偏高**，差评可能部分来自物流，但不足以解释 22.25% 的差评率。
3. **unknown 品类差评率 18.16%**，高于平均。这类商品连品类都没填，通常是**小卖家、低质量 listing**，差评率高是合理的——**这反过来验证了清洗时保留 `unknown` 而不是删除的决定是对的**，它本身就是个有信息量的信号。

> **分析方法的要点**：判断"差评是不是物流造成的"，要看**该品类延迟率 vs 全站延迟率**的对比。如果差评率高但延迟率正常，问题就不在物流。这是"排除法"归因，比笼统说"提升服务质量"有用得多。

### Q10 支付：信用卡占 74%，分期把客单价拉高 2.8 倍

| 支付方式        | 订单数    | 占比    | 平均金额   | 平均分期数 |
| ----------- | ------ | ----- | ------ | ----- |
| credit_card | 73,891 | 74.6% | 166.59 | 3.6   |
| boleto      | 19,479 | 19.7% | 144.65 | 1.0   |
| voucher     | 3,028  | 3.1%  | 114.93 | 1.1   |
| debit_card  | 1,512  | 1.5%  | 140.29 | 1.0   |

| 分期区间   | 订单数    | 平均金额       |
| ------ | ------ | ---------- |
| 不分期    | 47,494 | 120.45     |
| 2-3 期  | 22,487 | 135.69     |
| 4-6 期  | 15,967 | 182.24     |
| 7-12 期 | 11,779 | **333.52** |
| 12 期以上 | 183    | 419.35     |

**结论**：

1. **信用卡是绝对主力（74.6%）**，`boleto`（巴西特有的银行票据支付）占 19.7%——这是巴西市场的本地化特征，做跨境业务必须支持。
2. **分期数与客单价强正相关**：7-12 期订单的平均金额（333.52）是不分期（120.45）的 **2.77 倍**。
3. **voucher（代金券）有 63.34% 是多笔支付**——因为代金券通常不能覆盖全额，需要组合其他支付方式。**这个字段的业务含义必须理解，否则会误判为"支付异常"。**

> **要点（因果方向）**：不能说"分期导致高客单"。更合理的解释是**反向因果**——买贵东西的人更需要分期。要验证这一点，需要看同一商品在"支持分期/不支持分期"下的转化率差异。

### Q11 RFM 分层：15.8% 的"重要流失客户"贡献了 29.4% 的收入

| 分层         | 客户数        | 人数占比       | 平均最近购买    | 平均次数 | 平均消费       | 收入占比       |
| ---------- | ---------- | ---------- | --------- | ---- | ---------- | ---------- |
| 新客         | 36,652     | 38.70%     | 93 天      | 1.00 | 164.71     | 38.49%     |
| **重要流失预警** | **14,984** | **15.82%** | **394 天** | 1.07 | **307.97** | **29.42%** |
| 一般客户       | 20,043     | 21.16%     | 215 天     | 1.09 | 164.52     | 21.02%     |
| 一般流失客户     | 22,898     | 24.18%     | 397 天     | 1.00 | 72.74      | 10.62%     |
| 重要价值客户     | 121        | 0.13%      | 93 天      | 3.54 | 565.31     | 0.44%      |
| 高频活跃客户     | 5          | 0.01%      | 59 天      | 3.00 | 118.85     | 0.00%      |

**结论**：

1. **最大的机会在"重要流失预警"**：14,984 人（15.8%），平均消费 307.97 元（是全站均值 160 的 **1.9 倍**），但已经 394 天没来了。**这群人贡献了 29.4% 的历史收入，是最该做召回的对象。**
2. **"重要价值客户"只有 121 人（0.13%）**——这个数字看着惨淡，但它是真实的。在 98% 客户只买一次的平台上，高频高价值客户本就是极少数。
3. **"一般流失客户"人数最多（24.18%）但平均消费只有 72.74 元**，是低价值一次性客户，召回成本不划算。**分层运营的核心就是区分这两类流失客户。**

> **技术点（这里最大的坑）**：`F`（频次）绝对不能用 `NTILE`。
>
> 本数据 96.96% 的客户只买过 1 次（91,832 / 94,707）。当大量值并列时，`NTILE(5)` 会把同分的人**随机劈到不同桶**——我第一次跑出来的结果是"高频客户"平均购买次数 **1.05 次**，明显荒谬。修正方式：对严重偏斜的离散字段改用业务阈值分箱（1 次 / 2 次 / 3-4 次 / 5 次以上）。
>
> **这是 NTILE 的经典陷阱**：它保证桶内数量相等，不保证桶内值有区分度。连续且分布均匀的字段（R、M）可以用，高度离散的字段（F）不能用。

## 四、三个"差点算错"的坑（这部分最值钱）

这三个坑的共同点：**SQL 不报错，结果看起来正常，但结论完全错误。**

### 坑 1：留存率全是 0

```sql
-- 错误写法
PERIOD_DIFF(DATE_FORMAT(o.purchase_ts,'%Y%m'),
            DATE_FORMAT(f.cohort_month,'%Y%m'))
```


`cohort_month` 已经是 `'2017-01'` 字符串，`DATE_FORMAT('2017-01', '%Y%m')` 返回 **NULL**（不是报错），`PERIOD_DIFF` 跟着返回 NULL，所有 `month_no` 都不等于 1/2/3，**留存率全算成 0**。

```sql
-- 正确写法
PERIOD_DIFF(DATE_FORMAT(o.purchase_ts,'%Y%m'), REPLACE(f.cohort_month,'-',''))
```

**教训**：聚合函数遇到 NULL 会静默返回 NULL，不会报错。**每个派生字段都要验证非空率。**

### 坑 2：延迟订单的平均超时是 −8.7 天

```sql
-- 错误写法：把 88,644 条提前送达的负值也平均进去了
ROUND(AVG(o.late_days), 1) AS 延迟订单平均超时天数
```

**教训**：`AVG()` 会平均整列，不会自动过滤。**任何"分组内的平均值"都要确认分母到底是谁。** 正确写法是 `AVG(CASE WHEN is_late = 1 THEN late_days END)`。

### 坑 3：is_late 和 late_days 自相矛盾

清洗时 `is_late` 用时间戳比较（`delivered_ts > estimated_ts`），而 `late_days` 用 `DATEDIFF`。`estimated_ts` 的时间部分是 `00:00:00`，所以**当天下午送达**会得到 `is_late = 1` 但 `late_days = 0`。

实测 1,292 单（占延迟订单的 14.2%）属于这种矛盾。修正后延迟率从 **8.11% → 6.77%**。

**教训**：同一个业务概念在两张表/两个字段里用了不同口径，是最隐蔽的数据质量问题。**必须做交叉校验**（`SUM(is_late=1 AND late_days<=0)` 应该等于 0）。

## 五、设计问答（基于真实产出）

**Q：你的项目里最有技术含量的是什么？**

> 不是写了多复杂的 SQL，而是**发现并修正了三个"不报错但算错"的问题**。比如留存率，`DATE_FORMAT` 对已经是字符串的月份返回 NULL，导致所有留存率算成 0，SQL 完全不报错。我是通过"留存率不可能全为 0"这个业务常识发现异常的。数据工程里最危险的不是报错，是静默失败。

**Q：复购率怎么算？**

> 三层：第一层，必须用 `customer_unique_id` 而不是 `customer_id`，否则每单都是新客、复购率恒为 0。第二层，要剔除同日多单，因为那是拆单不是复购——我的数据里 29% 的"复购"是同日拆单，剔除后从 3.04% 降到 2.17%。第三层，要说明观察窗口，窗口外的复购看不到。

**Q：NTILE 有什么坑？**

> 值大量并列时会随机分桶。我的客户频次 96.96% 是 1 次，用 `NTILE(5)` 分层后"高频客户"的平均购买次数只有 1.05 次，明显失真。连续均匀的字段可以用 NTILE，离散偏斜的必须用业务阈值分箱。

**Q：怎么证明延迟导致差评？**

> 现在只能证明相关：延迟 4-7 天的差评率 68%，准时是 9.5%。但不能排除混淆变量——偏远地区订单既慢、商品质量可能也差。要证因果需要控制品类和价格带做分层对比，或者做 A/B 测试（对同一批订单随机承诺不同时效）。

**Q：GMV 掉了我怎么排查？**

> 先拆维度，不要先猜。按公式拆：GMV = 订单数 × 客单价，先定位是量跌还是价跌。再按时间（是不是大促透支）、地域（是不是某个州物流出问题）、品类（是不是头部品类下滑）、渠道拆。我的项目里 2017-12 GMV 环比 −26.5%，一查就是 11 月黑五透支，属于预期内，不用干预。

**Q：你数据里最大的问题是什么？**

> 98% 的客户只买一次，复购率只有 2.17%，留存 M1 不到 0.7%。这不是我的数据有问题，是这个平台的真实业务特征。**分析的价值不是把数字做好看，是让业务方知道"这里没有复购红利，别把预算投在会员体系上"。**
